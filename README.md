# planee

A local-first app generated by [local-sync-template]. Two pieces:

- **frontend/** — static Astro + Svelte 5 app. IndexedDB is the source of
  truth; works fully offline.
- **backend/** — Go sync server (SQLite). Accepts pushes with last-write-wins
  conflict resolution and serves pulls from a monotonic cursor. Can also serve
  the built frontend so everything runs on one origin.

## Tables

- `project` — 2 columns (Project page)
- `version` — 2 columns (Version page)
- `task` — 4 columns (Task page)
- `version_task` — 2 columns (Version task page)
- `task_type` — enum, 4 values (no page; a dropdown wherever a column references it)
- `preferences` — 1 column (Preferences page)
- `status_type` — enum, 6 values (no page; a dropdown wherever a column references it)

Every table also carries the sync fields `id`, `updated_at`, `deleted_at`,
`server_seq` — see `backend/README.md` for how sync works.

## Quickstart

```sh
# 1. backend
cd backend
go run .                      # http://localhost:8228

# 2. frontend (new terminal)
cd frontend
npm install
npm run dev                   # http://localhost:4321
```

Open Settings in the app and set the sync URL to `http://localhost:8228`,
then "Sync now". For production, build the frontend and let the backend serve
it same-origin:

```sh
cd frontend && npm run build
cd ../backend
STATIC_DIR=../frontend/dist go run .    # PowerShell: $env:STATIC_DIR='../frontend/dist'; go run .
```

Or with Docker. A prebuilt multi-arch image is published to
`ghcr.io/descent098/planee` by `.github/workflows/docker.yaml`, so a
deploy is just:

```sh
docker compose up -d          # pulls ghcr.io/descent098/planee:latest
# app + sync API → http://localhost:8228, database → ./data/planee.db
```

Prefer building from source? `docker compose -f docker-compose.build.yml up --build`.
See [DEPLOYMENT.md](DEPLOYMENT.md) for the full pipeline (tags, GHCR setup, backups).

## Evolving the schema

The schema lives in four places that must change together:

1. `backend/sql/schema.sql` — the DDL (applied to fresh databases only).
2. `backend/sync.go` — `tableOrder` + `tables` metadata.
3. `frontend/src/lib/db/types.ts` + a new migration appended in
   `frontend/src/lib/db/db.ts`.
4. `frontend/tests/sync/helpers/schema.ts` — the test harness keeps its own
   mirror of the schema on purpose, so it cannot inherit a drift in the app's.

Enum tables (`task_type`, `status_type`) are reference data, not user rows: their values are
seeded by `schema.sql` and by the first `db.ts` migration, the app never writes to
them, and they are left out of sync and backups. Changing a value list is a
schema change — see the ENUM note in `docs/dev/planning/TODO`.

The full per-change checklist (including what a brand-new table needs beyond
these) is in `docs/dev/planning/TODO`.

Foreign keys are plain `REFERENCES` with soft deletes — there are no cascades.
When deleting a parent row, clean up child rows in app code.

### Single-row (settings-style) tables

If a table is meant to hold ONE logical row for the whole account (user
settings, a profile, app preferences), do **not** create that row with
`withSyncFields()` — it mints a random UUID per device, so each device
creates its own copy and reads like `(await all('user_settings'))[0]` pick a
different row on different devices after sync. Use the singleton helpers in
`frontend/src/lib/db/repo.ts` instead:

```ts
import { getSingleton, putSingleton } from './lib/db/repo';

const settings = (await getSingleton('user_settings')) ?? DEFAULTS;
await putSingleton('user_settings', { ...settings, theme: 'dark' });
```

Both write under one fixed id (`'singleton'`), so every device converges on
the same row and concurrent edits resolve last-write-wins.

If a table was already populated with the buggy random-id pattern (or a server
sends duplicates), reconcile on read: pick the best row (e.g.
newest `updated_at`), `putSingleton` it, and `softDelete` the rest — a few
lines that heal the store idempotently.

### Storing rows: go through the repo helpers

`put`/`bulkPut` in `src/lib/db/repo.ts` JSON round-trip each row before writing
it. That is not cosmetic: IndexedDB structure-clones values, and Svelte 5
`$state` proxies are **unclonable** — passing reactive state (an array of
selected ids, or a whole row read back from a `$state` list) straight to
`getDB().put` throws `DataCloneError`, silently in a fire-and-forget handler.
Always write through the repo helpers.

## Versioning & releases

The current version is the entire content of [VERSION](VERSION) (plain semver,
starting at 0.1.0 — `cat VERSION` in scripts/CI), with history in
[CHANGELOG.md](CHANGELOG.md). To cut a release:

1. **Bump VERSION** — patch (0.1.0 → 0.1.1) for fixes, minor (0.1.0 → 0.2.0)
   for new features, major for breaking changes. A schema change that needs a
   migration is at least a minor bump.
2. **Close out the CHANGELOG.md heading.** Entries accumulate under the topmost
   `(unreleased)` heading as you work, split across Features / Bug Fixes /
   Other. Releasing means replacing `(unreleased)` with the date and opening a
   fresh `<next> (unreleased)` heading above it. Call out schema changes
   explicitly so other devices' owners know an upgrade touches the data model.
3. **Commit, tag, and push.** Tagging `v<VERSION>` publishes a matching Docker
   image to `ghcr.io/descent098/planee` (`:0.2.0`, `:0.2`, `:0`) via
   `.github/workflows/docker.yaml` — see [DEPLOYMENT.md](DEPLOYMENT.md):

```sh
git add VERSION CHANGELOG.md && git commit -m "Release $(cat VERSION)"
git tag "v$(cat VERSION)" && git push && git push --tags
```

## Notes

- Single-user by design: there is no auth. Run it on a LAN or behind your own
  reverse-proxy auth if exposed.
- `GET /backup` on the backend downloads the SQLite file.
- Changing the sync server or restoring a backup calls `resetLocalSyncState()`,
  which drops the pull cursor and the remembered server identity, clears every
  row's `server_seq`, and re-queues every local row — so the next sync
  reconciles from scratch instead of silently forking. See
  `backend/README.md` › Sync gotchas.
- Docs live in [docs/](docs/): `docs/dev/` for how it is built (start with
  `docs/dev/planning/TODO`), `docs/user/` for how it is used.
